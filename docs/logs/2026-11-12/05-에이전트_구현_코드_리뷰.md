# LLM 분석 에이전트 구현 범위 코드 리뷰

## 요청

커밋 `bd6fd6080f1a4a599c2cb68a8fcf13b4b0328dac` ~ `f3608c6691dcaa0fb580afc67d44e08974e2610b` 범위의 코드 리뷰. 코드를 읽고 판단했으며 실제 스택을 띄워 재현하지는 않았다. 이 로그는 리뷰 결과 기록이고 코드 수정은 하지 않았다.

## 리뷰 결과 (10건)

### 높음

1. **차트가 화면에 그려지지 않음** — `frontend/src/components/agent/AnswerChart.tsx:18`
   - 백엔드는 `asdict(self.chart)`로 `step_id`(snake_case)를 보내고(`agent/app/agent/tools/final_answer.py:86`), 프론트는 `chart.stepId`를 읽는다. `store._row`는 최상위 컬럼만 camelCase로 바꾸므로 이 필드는 변환되지 않는다.
   - `steps.find`가 결과를 못 찾아 컴포넌트가 `null`을 반환한다. 실시간 응답과 히스토리 모두 차트가 사라진다.
   - 수정: 프론트 타입을 `step_id`로 맞추거나 서버에서 camelCase로 변환한다.

### 중간

2. **연결이 끊기면 run이 'running'으로 남음** — `agent/app/agent/loop.py:223`
   - `yield AgentEvent("started")`가 try/finally보다 앞에 있다. 이 시점에 `aclose()`가 호출되면 실패 처리와 `_finish`가 실행되지 않아 상태가 영구히 'running'이고 트레이스·메트릭도 남지 않는다.
   - 수정: yield를 try 안으로 옮긴다.

3. **엔드포인트마다 LLM 클라이언트·Executor를 따로 생성** — `agent/app/api/ask.py:77`
   - `/agent/ask`와 `/agent/runs`가 각각 `build_llm_client`, `build_executor`를 호출한다. Groq 요청 간격(2초), 폴백 쿨다운, 커넥션 풀, `TenantTokens` 캐시가 엔드포인트 단위로 분리되어 Groq 무료 한도(30 RPM)를 넘어 429가 날 수 있다.
   - 수정: `app.state`에 하나만 만들어 공유한다(`get_knowledge_context`와 같은 방식).

4. **413 한 번에 run 전체가 로컬 모델로 고정됨** — `agent/app/config.py:60`
   - 413이 기본 폴백 대상 상태 코드에 있어 `FallbackSession.chat`이 Ollama로 전환하고 `_index=1`로 고정한다. 히스토리를 줄여 재시도하는 루프의 413 처리(`loop.py:338`)가 실행되지 않는다.
   - 수정: 루프에서 먼저 처리하거나 413에서는 세션을 고정하지 않는다.

5. **동시 run이 같은 에러 객체를 공유** — `agent/app/llm/fallback.py:146`
   - 쿨다운 중 새 세션이 `owner.last_error(0)`의 같은 `LLMError` 인스턴스를 받고, `_with_wait`가 그 객체의 `wait_ms`를 덮어쓴다. 동시 run의 시간 예산 계산이 서로 영향을 받는다.
   - 수정: raise 전에 복사하거나 새로 감싼다.

### 낮음

6. **`events` 시간 필터 검사 우회 가능** — `agent/app/sql/guard.py:182`
   - `WHERE timestamp = timestamp`, `... OR true`, 조인된 다른 테이블의 `timestamp` 비교도 `_clause_has_time_predicate`를 통과한다. 남는 방어는 플랜 비용 검사와 statement timeout뿐이다.
   - 수정: 최상위 AND 조건 중 `events.timestamp`를 컬럼이 아닌 값과 비교하는 것을 요구한다.

7. **DSN 비밀번호 이스케이프 없음** — `agent/app/config.py:124`
   - 공백·`'`가 든 비밀번호는 libpq가 잘못 파싱해 접속에 실패한다. agent-db-roles 쪽은 `%L`로 설정하므로 DB는 정상이라 원인 파악이 어렵다.
   - 수정: `password='...'`로 감싸고 `\`, `'`를 이스케이프하거나 psycopg 키워드 인자로 전달한다.

8. **승격된 난이도가 저장되지 않음** — `agent/app/agent/loop.py:651`
   - `done` 이벤트(`_summary`)는 승격된 `state.budget.difficulty`를 보고하지만 `RunTotals.difficulty`, `metrics.record_run`, 트레이스 태그는 최초 분류값 `run.difficulty`를 쓴다. 히스토리와 Prometheus/Grafana 집계가 실제 사용한 예산과 어긋난다.

9. **메트릭 포트가 모든 인터페이스에 노출됨** — `docker-compose.yml:138`
   - 에이전트 `:8000`(인증 없는 `/metrics`, `main.py:57`)과 백엔드 `:9091`(Actuator)이 외부에 열려 있다. 에이전트 API도 nginx를 우회해 직접 접근된다.
   - 수정: `127.0.0.1`에 바인딩한다. Prometheus는 compose 네트워크로 수집하므로 영향 없다.

10. **LLM 미호출인데 강제 호출 횟수 소모** — `agent/app/agent/loop.py:325`
    - `must_answer` 상태에서 `forced_calls`를 올린 뒤 `_fit`이 `None`을 반환하면 모델을 호출하지 않고도 2회 중 1회가 소모되어 `NO_CONCLUSION`(`budget_exhausted`)으로 끝날 가능성이 커진다.
    - 수정: 413 경로(`loop.py:342`)처럼 카운트를 되돌린다.
