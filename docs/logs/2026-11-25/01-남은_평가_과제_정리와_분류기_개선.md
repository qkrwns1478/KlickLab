## 작업 내용

### 1. 루프 실행 지표에 추론 토큰 집계 (`evals/report.py`, `evals/run_eval.py`)

- 원인: 루프의 실행 요약(`usage`)에는 `reasoning_tokens`가 이미 들어 있었다. 그런데 평가기의 `RunMetrics.of()`가 `prompt_tokens`·`completion_tokens`만 읽었고, `_golden_loop`도 이 값을 `GoldenResult`로 넘기지 않았다. 그래서 루프 리포트의 추론 토큰이 항상 0으로 나왔다.
- 수정:
  - `RunMetrics.reasoning_tokens`를 추가하고 실행 요약에서 읽는다.
  - `aggregate()`가 `reasoning_tokens_avg`를 낸다.
  - 난이도별 표의 열을 "출력(추론) 토큰"으로 바꿨다.
  - 루프 golden 결과에도 추론 토큰을 채운다.
- 실행 로그 DB(`agent_runs`)에는 추론 토큰 열을 추가하지 않았다(스키마 변경 없음).
- 테스트: `test_run_metrics_and_aggregate_by_difficulty`에 추론 토큰 검사를 추가했다.

### 2. 분류기 기준 수정 (`app/agent/prompts.py` `CLASSIFY_SYSTEM_PROMPT`)

11-13 원인 분석에서 compare로 분류된 문항은 diag-05, 06, 07, 08, 11이었다. 실패한 문항(diag-05, 11)은 compare 예산(툴 6회) 중 2회만 쓰고 끝났다. 따라서 예산이 모자라서 실패한 것이 아니라 탐색이 얕아서 실패한 것이다.

- 기존 기준은 "추이를 보는 질문 = compare"였다. diagnose는 "변화의 원인이나 이상 징후"로만 정의돼 있었다. 그래서 "방문 행동이 어떻게 달라?"처럼 볼 지표가 정해지지 않은 열린 질문이 compare로 갔다.
- 수정 내용:
  - **lookup**: 한 지표의 일별 추이와 한 기준의 그룹별 집계·상위 N개를 포함한다.
  - **compare**: 볼 지표가 질문에 나와 있고, 두 기간이나 여러 그룹을 한두 번 조회해 비교하면 되는 질문이다.
  - **diagnose**: 다음 중 하나에 해당하는 질문이다.
    - 원인·이유·근거를 묻는다.
    - 볼 지표가 정해지지 않은 열린 질문이다(행동·패턴, 구매 의도, 성과 평가).
    - 이상 징후를 찾는다.

분류만 따로 측정했다(golden 44문항의 `category` + 원인 분석 12문항 = diagnose). 측정 스크립트는 임시로 scratchpad에 두었고 저장소에는 넣지 않았다.

| 정답 분류 | OpenAI 수정 전 (3회) | OpenAI 수정 후 (3회) | 로컬 gpt-oss-20b 수정 후 (1회) |
| --- | --- | --- | --- |
| lookup | 85.1% (74/87) | **94.3% (82/87)** | 100% (29/29) |
| compare | 80.0% (36/45) | 80.0% (36/45) | 73.3% (11/15) |
| diagnose | 58.3% (21/36) | **83.3% (30/36)** | 91.7% (11/12) |

- 수정 후에도 compare로 가는 diagnose 문항은 diag-05("이탈률이 특히 높은 채널은 어디고 얼마나 차이 나?")와 diag-07("트래픽이 몰리는 시간대, 기기별 차이")이다. 두 문항은 볼 지표가 질문에 나와 있어 compare로 보는 것도 타당하다. 평가셋 라벨이 diagnose라서 오분류로 셌다.
- compare → lookup 오분류(compare-03, 04, 10, 14: "요일별 하루 평균")는 남았다. lookup 예산(SQL 1회)으로 시작하지만 루프에서 승격을 요청할 수 있다.
- 분류 정확도가 올라도 원인 분석 통과율이 오르는지는 아직 확인하지 않았다. diagnose 예산을 받아도 탐색 깊이가 그대로면 결과가 같을 수 있다. 7절의 평가로 확인한다.
- 로컬 수정 전 수치는 따로 재지 않았다. 11-13 로컬 원인 분석 실행에서 diagnose 정답은 6/12였다.

### 3. "오늘 포함" 정의 보강 (`app/agent/prompts.py`, `app/knowledge/catalog/glossary.yaml`)

- 기존 정의(이번 주·이번 달 = 오늘까지, 상한 없음)와 compare-01·12의 정답 SQL은 서로 맞았다. 모델이 "오늘 데이터는 일부만 있다"는 안내를 보고 오늘을 뺀 것이 원인이라고 보고, 정의는 바꾸지 않았다. 질문·정답 SQL도 고치지 않았다.
- 스키마 요약(prompt 모드)과 용어집 `period_week`·`period_month`(rag 모드)에 다음을 명시했다.
  - 이번 주·이번 달에는 오늘(부분 데이터)도 넣는다. 오늘을 빼는 것은 "최근 N일"뿐이다.
  - 기간의 일평균은 날짜별 합계를 먼저 구한 뒤 `avg()` 한다. 데이터가 있는 날짜 기준이며, 달력 일수로 나누지 않는다(compare-12).
- 용어집을 바꿨으므로 rag 평가 전에 지식 베이스를 다시 적재해야 한다(본문 해시가 달라 재임베딩된다).

### 4. diag-01 시드 의존 제거 (`evals/datasets/analysis_questions.yaml`)

- 원인: 시드는 캠페인을 실행일 기준 2~8일 전(`current_date - 8` ~ `- 2`)에 놓는다. 그런데 질문은 달력 주("지난주 대비 이번 주")였다. 그래서 수요일 이후에 시드하면 캠페인이 이번 주에 걸쳐 "이번 주에 줄었다"가 성립하지 않았다. 11-13 로그의 추정이 맞았다.
- 수정: 질문을 "어제는 그 전 7일보다 참여도가 떨어진 페이지가 있어? 있다면 원인을 분석해 줘"로 바꿨다. "그 전 7일"(2~8일 전)이 캠페인 기간과 정확히 겹친다. 검사 SQL도 "그 전 7일의 일평균 캠페인 세션 > 어제의 2배"로 바꿨다.
- 시드는 다른 문항(diag-04 "최근 일주일 사이 신규 방문자 증가", diag-09)이 같은 캠페인 기간을 쓰고 있어 바꾸지 않았다.
- 재시드 후 `run_eval check`로 성립 여부를 확인할 예정이다.

### 5. 기본 공급자를 OpenAI로 변경

| 파일 | 변경 |

- Groq·EXAONE 클라이언트 코드는 지난 리포트 재현용으로 남겼다.
- `agent/.env`에는 `LLM_PROVIDER`가 없어 지금까지 groq로 동작했다. 이제 기본값으로 openai가 된다.
- CI에서 LLM 평가를 돌리려면 저장소에 `OPENAI_API_KEY` 시크릿을 등록해야 한다. 프록시를 쓰면 `OPENAI_BASE_URL` 변수도 등록한다. 워크플로 실제 실행은 하지 않았다.
- gpt-6-luna 단가를 몰라 비용은 계속 비어 있다.

### 6. 폴백 허용 난이도: 유지

- 11-12에 "전체 허용"으로 정할 때 "Groq 기준선이 생기면 다시 판단한다"는 조건을 달았다. Groq를 더 쓰지 않으므로 기준 공급자는 OpenAI가 된다.
- OpenAI는 한도가 커서(요청 30,000/분, 토큰 1억 8천만/분) 폴백은 장애나 402가 날 때만 탄다. 로컬 품질(compare 53.3%, diagnose 18.2%)은 낮다. 그래도 개발 환경 전용이고, 응답에 폴백 표시가 붙으며, 한도 안내만 하는 것보다 낫다는 기존 근거는 그대로다. 그래서 결정을 바꾸지 않았다. 코드 변경은 없다.

### 9. diagnose 탐색 깊이 수정 (2026-11-26)

8절에서 원인 분석이 실패한 원인을 탐색 깊이로 보았다. 모델이 처음 본 지표에서 멈추거나(diag-11: SQL 1회로 결론), 한 관점만 반복하다 예산을 다 썼다(diag-01). 이를 두 겹으로 고쳤다.

#### 원인 분석 절차 안내 (`app/agent/prompts.py` `DIAGNOSE_GUIDE`)

- diagnose 실행의 시스템 프롬프트에만 덧붙인다. 실행 도중 diagnose로 승격되면 시스템 메시지로 한 번 넣는다.
- 안내 내용:
  - 결론 전에 다른 관점을 두세 개 고른다. 관점은 유입, 기기, 방문자 유형(신규·재방문, 회원·비회원, 방문자당 세션 수), 페이지·퍼널, 시간이다.
  - 차이가 보이는 구간은 한 단계 더 나눠 본다.
  - "어떻게 다른가" 질문에는 방문자 단위 지표도 본다.
  - 같은 관점의 쿼리를 조건만 바꿔 반복하지 않는다.
  - 여러 지표는 한 쿼리로 묶는다.
  - 작은 표본으로 결론 내지 않는다.

#### 이른 제출 되돌림 (`app/agent/loop.py` `_too_early`)

- diagnose에서 SQL을 3회(`DIAGNOSE_MIN_SQL`) 돌리기 전에 `submit_report`를 내면 한 번만 되돌린다. 되돌릴 때 다른 관점을 더 보라는 메시지를 돌려준다.
- 되돌린 제출은 툴 예산에 넣지 않는다.
- 다음 경우에는 되돌리지 않는다.
  - 결론 강제 단계
  - SQL·툴 예산이 남지 않은 경우
  - 예산의 80%를 넘긴 경우
- 모델이 같은 결론을 다시 내면 그대로 받는다.
- 변경에 따라 `RunState.early_submit_checked` 필드를 추가했다.

#### 공급자별 입력 토큰 상한 (`app/config.py` `Settings.max_prompt_tokens`)

- 탐색 깊이 수정의 첫 평가에서 diag-04 답변 2건에 "결과에 열 이름만 표시되고 수치 행이 없다"는 문장이 나왔다.
  - 원인은 `AGENT_MAX_PROMPT_TOKENS` 기본값 4,800이었다. 이 값은 Groq 무료 등급 TPM 8K 때문에 정했는데, OpenAI에도 그대로 걸렸다. 그래서 이력이 길어지는 diagnose에서 결과 행이 압축돼 빠졌다.
  - 따라서 **8절과 9절 첫 평가의 OpenAI 루프·원인 분석 수치는 모두 이 상한 아래에서 측정한 값이다.** 11-13 OpenAI 루프는 `AGENT_MAX_PROMPT_TOKENS=0`을 직접 줘서 돌렸다.
- 수정: 설정을 비우면(새 기본값) 공급자별 값을 쓴다.
  - groq: 4,800
  - local: `num_ctx`의 75%(기본 24,576)
  - openai 등: 제한하지 않는다(0)
  - 폴백이 켜져 있으면 두 공급자 중 작은 값을 쓴다.
  - 값을 지정하면 그 값이 우선한다.
