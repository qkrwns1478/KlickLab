# LLM 분석 에이전트 Phase 3: 지식 베이스 (RAG)

## 요청

`docs/plans/01-text_to_sql_LLM_분석_에이전트_구현_계획.md`의 Phase 3 구현.
LLM 테스트는 **K-EXAONE 2.5** 기준으로 진행했다.

## 작업 내용

### 1. 시맨틱 레이어 YAML (`app/knowledge/catalog/`)

| 파일 | 문서 수 | 내용 |
| --- | --- | --- |
| `tables.yaml` | 17 | agg_* 10개, events, conversion_events, 배치 집계 5계열(minutes/hourly/daily/weekly 묶음). 요약·grain·컬럼(타입·설명)·참고·`use_for` |
| `metrics.yaml` | 17 | 순 방문자, 세션, 페이지뷰, 이탈률, 참여율, 전환율·전환 수, 매출, 결제·가입·클릭 수, 평균 세션 시간, 페이지 체류 시간·종료율, 결제 세션 비율, 페이지 이동 전환율, 신규/재방문 |
| `glossary.yaml` | 13 | 기간 표현(오늘·어제 / 최근 N일 / 이번 주·지난주 / 이번 달·지난달), 요일, 시간대, 데이터 공통 규칙, 유입 경로·채널 그룹, 캠페인, 이벤트, 페이지, 기기·OS·브라우저·지역, 성별·연령 |
| `examples.yaml` | 9 | 질문–SQL 예시. golden 문항과 겹치지 않게 새로 작성(평가 결과 오염 방지) |

- 지표 정의는 백엔드 `RollupService`(참여 세션 = 10초 이상 체류 또는 2페이지 이상 또는 전환)와 Controller 계산식을 기준으로 했다.
- 값 도메인(지역·OS·브라우저·속성 키 등)은 데모 DB에서 직접 조회했다.

### 2. 문서 로더·임베딩·인덱서

- `knowledge/documents.py`: YAML → `KnowledgeDoc(kind, name, title, content, metadata)`. 이름 중복·필수 항목 누락은 `CatalogError`.
- `llm/embedding.py`: `EmbeddingClient` 프로토콜 + `LocalEmbedding`(sentence-transformers, **BAAI/bge-m3**, 1024차원 = V4 `vector(1024)`). CPU 질의 임베딩 약 0.25초.
  - `[project.optional-dependencies] embedding`으로 분리하고 torch는 PyTorch CPU 인덱스로 고정했다(GPU 빌드는 이미지가 수 GB). 설치: `uv sync --extra embedding`, 첫 실행 때 모델 약 2.2GB 다운로드.
  - `EMBEDDING_PROVIDER=none`이거나 모델을 쓸 수 없으면 키워드 검색만 한다.
- `knowledge/indexer.py`(`python -m app.knowledge.indexer [--force] [--no-embedding]`): 본문 해시·임베딩 모델이 같으면 다시 임베딩하지 않고, 카탈로그에 없는 문서는 지운다. 56건 전체 임베딩 16초.

### 3. 하이브리드 검색 (`knowledge/retriever.py`)

세 신호의 순위를 RRF(Σ 1/(60+rank))로 합친다.

| 신호 | 방식 |
| --- | --- |
| vector | pgvector 코사인 거리 |
| keyword | 질문을 단어로 나눠(조사·서술어 제거) `word_similarity × idf` 합. pg_trgm이 한국어 trigram을 처리하는 것을 먼저 확인했다 |
| alias | 지표·용어 문서의 별칭·제목이 질문에 그대로 있으면(공백 무시) 후보로 올림. 긴 별칭 우선 |

- 처음 버전(벡터+키워드 단순합, 공용 후보 20개를 종류별로 나눔)은 기간 표현 문서가 테이블·지표 문서에 밀려 빠졌다. → **종류별로 따로 검색**하고, 키워드 점수에 **idf**를 넣고(‘세션’, ‘페이지’처럼 흔한 단어의 영향 축소), **별칭 신호**를 추가했다.
- `context(question, quota)`: 종류별 할당량만큼 문서를 골라 시스템 프롬프트에 넣는다. 기본 `table:2,metric:2,glossary:3,example:1`.

### 4. 프롬프트·파이프라인 연결 (`KNOWLEDGE_MODE=prompt|rag`, 기본 prompt)

- `knowledge/context.py`: rag 모드의 스키마 컨텍스트 = 데이터 개요 + **조회 가능한 테이블 목록(한 줄씩, 항상)** + 검색 문서. 테이블 목록은 검색이 테이블 문서를 놓쳐도 모델이 테이블 이름을 알게 하려고 넣었다(실제로 events 문서를 놓친 2문항도 정답이었다). 임베딩 모델은 프로세스에 하나만 둔다(`/agent/ask`·`/agent/runs` 공유).
- Phase 1 단일 턴(`TextToSQL`)·평가 러너: rag 모드면 검색 문서로 SQL 프롬프트를 만든다. `run_eval --knowledge rag --quota …`, 리포트에 넣은 문서와 검색 지연을 남긴다.
- Tool Loop: rag 모드면 시스템 프롬프트에 검색 문서를 넣고 **`search_knowledge(query, kind?)`** 도구를 연다.
  - 이미 보여 준 문서(프롬프트·이전 검색)는 이름만 돌려준다(토큰 절약). 같은 검색은 예산을 차감하지 않고 거절한다.
  - 이력 압축 level 1 이상에서는 이전 검색 결과의 본문을 뺀다.
  - 검색이 실패하면 스키마 요약(prompt 모드)으로 진행한다. `classified`·`done` 이벤트에 넣은 문서 목록을 싣는다.
- prompt 모드의 프롬프트는 Phase 1~2와 같다(기준선 유지).

### 5. 검색 평가 (`evals/run_retrieval_eval.py`, LLM 호출 없음)

golden 20문항에 "풀이에 필요한 문서"를 정의했다: 정답 SQL이 쓰는 테이블(sqlglot으로 추출) + 문항별 `knowledge` 라벨(지표·용어, `golden_sql.yaml`에 추가).

| 방식 (할당량 2/2/3/1) | 재현율 | 전부 찾은 문항 | table | metric | glossary |
| --- | --- | --- | --- | --- | --- |
| **hybrid (vector + keyword + alias)** | **95.0%** | 17/20 | 90.0% | 93.8% | 100% |
| vector만 | 81.2% | 9/20 | 85.0% | 87.5% | 73.3% |
| keyword만 | 82.5% | 10/20 | 90.0% | 56.2% | 93.3% |

- 개선 과정(할당량 3/3/3/2): 단순 hybrid 91.7% → idf + 종류별 검색 + 별칭 **98.3%**. 할당량 2/2/2/0은 92.5%.
- 벡터는 지표 문서에 강하고 기간 표현(용어)에 약하며, 키워드는 반대다. 둘을 합쳐야 두 종류 모두 90% 이상이 된다.
- 리포트: `agent/evals/reports/20261111-1349-retrieval-quota-2231.md`

## 성능 측정: 프롬프트 직접 주입 vs RAG (K-EXAONE 2.5, high, golden 20문항)

할당량을 **스키마 요약과 비슷한 컨텍스트 크기**로 맞춰 정확도를 비교했다(시스템 프롬프트 평균 prompt 5,087자 / rag 5,139자).

| 방식 | 실행 정확도 | 평균 입력 토큰 | 평균 출력 토큰(추론) | 생성 지연 평균 / 중앙값 |
| --- | --- | --- | --- | --- |
| prompt (Phase 1 기준선, 09:42) | 100% (20/20) | 1,691 | 944 (827) | 20.2s / 13.5s |
| rag (2/2/3/1, 13:49) | 95% (19/20) | 1,842 | 1,263 (1,134) | 51.8s / 40.1s |

- 실패 1건(compare-05)은 값은 맞지만 두 기간을 열이 아닌 행으로 돌려준 경우다. Phase 1 low effort의 실패와 같은 모양이며 지식 문서 누락 때문은 아니다(필요 문서 모두 포함).
- **토큰은 줄지 않았다.** 테이블 17개짜리 스키마는 요약 전체가 약 1,700토큰이라, 문서 단위로 검색해 넣어도 비슷한 크기가 된다. 할당량을 3/3/3/2로 늘리면 6,557자로 오히려 커진다. 이 규모에서 RAG의 이점은 토큰 절감이 아니라 (1) 카탈로그가 커져도 프롬프트 크기가 고정되는 점, (2) 요약에 못 넣는 예시 SQL·참고 사항을 필요할 때 넣을 수 있는 점이다.
- 출력 토큰 +34%, 지연 2.5배. rag 문서는 정의·주의사항이 많아 추론이 길어진 것으로 보이지만, 두 실행 시각이 달라 서버 부하 차이를 분리하지 못했다.
- 리포트: `agent/evals/reports/20261111-1349-golden_sql-k-exaone_v2_5-high-rag.md`

### 결론

- 지금 평가셋·스키마 규모에서는 **prompt 모드를 기본값으로 유지**한다. rag는 같은 정확도 수준(1문항 차이, 형식 문제)이지만 토큰·지연 이점이 없다.
- 변별력 있는 비교는 Phase 4에서 문항을 늘린 뒤(특히 스키마 요약에 없는 지표·events 드릴다운) 다시 한다.

## Tool Loop 실측 (K-EXAONE 2.5)

- 문서에는 `tools` 파라미터 설명이 없지만 **K-EXAONE도 tool calling을 지원한다**. 한 응답에 `search_knowledge` 병렬 호출 2개를 돌려주는 것을 확인했고, `tool` 역할 메시지가 들어간 다음 턴도 정상 처리했다. `AGENT_MAX_PROMPT_TOKENS=0`, `AGENT_STEP_MAX_TOKENS=8192`로 실행했다(Groq 대응 상한은 불필요).

| 실행 | 결과 | LLM 호출 | 입력/출력 토큰 | 지연 |
| --- | --- | --- | --- | --- |
| rag lookup "어제 순 방문자 수는?" | succeeded, 575명(근거 step 1) | 3 | 5,535 / 317 | 19.7s |
| rag diagnose "지난주 대비 이번 주 참여도가 떨어진 페이지와 원인" | budget_exhausted(툴 호출), 근거 연결된 결론 | 8 | 41,730 / 11,002 | 1,031s |
| prompt diagnose (같은 질문) | budget_exhausted(시간), SQL 0회 | 4 | 7,988 / 2,333 | 315s |

- rag diagnose 흐름: `search_knowledge`(페이지 참여도 지표) → `describe_table` 2회 → SQL 7회(그중 `round(double precision, int)` 오류, 없는 컬럼 오류를 **모델이 스스로 고침**) → 툴 호출 예산 소진 → 강제 결론. 결론은 /mypage 일평균 페이지뷰 -23%, 종료율 32.1%→39.7% 등을 step 근거와 함께 제시하고 원인은 가설로 남겼다. 시드에 심은 원인(캠페인 유입 변화 등)까지는 가지 못했다.
- 1,031초 중 약 700초는 **강제 결론 호출 한 번**이다. `rateLimitWaitMs=7000`이 재시도 백오프 1+2+4초와 같아, 180초 읽기 타임아웃이 3번 난 뒤 재시도로 성공한 것으로 보인다. 시간 예산은 호출 사이에서만 확인하므로 진행 중인 호출을 끊지 못한다.
- prompt diagnose는 첫 호출 하나가 180초를 넘겨 시간 예산이 바로 소진됐다. 이때 거부 메시지가 "툴 호출 예산을 모두 썼다"로 나가 모델이 답변에 "도구 호출 예산(15회)이 소진"이라고 **사실과 다르게** 썼다. → `Budget.exhausted_reason()`을 추가해 실제 소진 항목(시간/툴 호출/토큰/입력 길이)을 알리도록 고쳤다.
- 두 diagnose 실행은 EXAONE 지연 편차가 결과를 좌우해 **prompt vs rag 비교로 쓸 수 없다.** 1회씩이라 통계적 의미도 없다.
- 이번 세션 EXAONE 사용: 약 36~39회(평가 20, tool calling 확인 1, 루프 15 + 타임아웃 재시도). 남은 호출 약 40회.

## 추가 작업: 모델 호출 시간 초과 처리

rag diagnose 실측에서 결론 제출 호출 하나가 약 11분 걸린 문제(읽기 타임아웃 180초 × 재시도)를 고쳤다.

- `LLMClient.chat(timeout=)`: 호출마다 응답 시간 제한을 줄일 수 있다. **응답 시간 초과는 재시도하지 않고** `status=408`(`TIMEOUT_STATUS`) `LLMError`로 낸다. 같은 요청은 같은 시간이 걸리고, 재시도 대기는 시간 예산에서 빠져 예산이 못 막았기 때문이다. 429/5xx 재시도는 그대로다.
- Tool Loop: 호출 타임아웃 = `max(남은 시간 예산, 30초)`, 결론 제출 호출은 60초. 시간 초과가 나면 `Budget.timed_out`으로 예산 소진 처리해 **모은 근거로 `submit_report`를 강제**하고, 그 호출도 시간 초과면 서버 요약으로 끝낸다(상태 `budget_exhausted`).
- 최악 소요 시간: 시간 예산 + 마지막 호출 제한(60초) + 시간 초과 시 30~60초 정도로 묶인다. 분류 호출은 아직 기본 타임아웃(180초)이다.
- 효과는 가짜 LLM 테스트로만 확인했다. EXAONE으로 diagnose를 다시 돌려 보지는 않았다(남은 호출 수 절약). 호출 하나가 60초 안에 끝나지 않으면 EXAONE에서는 결론을 내지 못하고 서버 요약으로 끝날 수 있다.
- 테스트 5건 추가(`pytest` **176건 통과**): 시간 초과 미재시도·408, 호출별 timeout 적용, 남은 예산 기반 timeout, 시간 초과 후 결론 강제, 반복 시간 초과 시 서버 요약.
