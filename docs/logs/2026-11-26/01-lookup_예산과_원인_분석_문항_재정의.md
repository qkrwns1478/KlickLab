## 작업 내용

### 1. lookup SQL 상한 1 → 2 (`app/agent/budget.py`)

- 11-26 로컬 Tool Loop의 compare-04("최근 7일 기기 유형별 결제 전환율")는 lookup으로 분류된 뒤 승격 없이 끝났다. SQL 2회가 모두 실패했고 `budget_exhausted`였다.
- 원인은 분류가 아니라 예산이다.
  - compare-03·04·10·14는 "한 기준의 그룹별 집계"라서, 11-25에 고친 분류 기준으로는 lookup이 맞다. 평가셋의 `category`는 SQL 유형 라벨이라 난이도 분류와 일치하지 않아도 된다.
  - DB 실행 오류도 SQL 예산을 차감한다(`test_agent_tools.py`로 고정된 설계). 그래서 lookup은 첫 SQL이 실패하면 승격 말고는 고칠 방법이 없었다.
- 수정: lookup `max_sql`을 2로 올렸다. 툴 호출 상한(3)은 그대로다. 실행 오류도 예산을 차감한다는 설계는 바꾸지 않았다.
- 분류 프롬프트(`CLASSIFY_SYSTEM_PROMPT`)는 바꾸지 않았다.
- 테스트:
  - `test_lookup_hides_run_sql_after_last_sql`를 `test_lookup_corrects_once_then_hides_run_sql`로 바꿨다. 실행 오류 뒤 한 번 고친 SQL로 성공하고, 그 뒤에는 `run_sql`이 빠지는지 검사한다.
  - `test_run_sql_refuses_when_sql_budget_is_spent`가 `LIMITS["lookup"].max_sql`을 쓰도록 했다.
- 로컬 모델로 compare-04를 다시 돌리지는 않았다.

### 2. 원인 분석 문항 재정의 (`evals/datasets/analysis_questions.yaml`)

#### diag-01: 시드가 만드는 것은 참여도 하락이 아니라 페이지뷰 하락

11-26 시드 DB에서 어제(11-25)와 그 전 7일(11-18 ~ 11-24)을 페이지별로 비교했다.

| 페이지 | 페이지뷰 (그 전 7일 일평균 → 어제) | 평균 체류 시간(초) | 종료율(%) |
| --- | --- | --- | --- |
| /products | 1,019 → 570 | 31.8 → 30.8 | 36.1 → 37.0 |
| / | 938 → 888 | 15.4 → 15.4 | 23.4 → 24.2 |
| /cart | 362 → 253 | 37.7 → 38.0 | 27.5 → 27.7 |
| /products/1 | 233 → 127 | 57.6 → 57.3 | 41.6 → 45.7 |

- 페이지 단위 참여도(용어집: 평균 체류 시간·종료율)는 큰 페이지에서 거의 변하지 않았다. 상품 상세 페이지별로는 몇 초·몇 %p씩 오르내리지만 방향이 일정하지 않고 표본이 작다.
- 페이지뷰는 캠페인 랜딩(/products*)에서 크게 줄었다. events로 나누면 /products*의 캠페인 유입 페이지뷰는 일평균 1,024 → 어제 1이고, 캠페인 외 유입은 1,809 → 1,669다.
- 따라서 이전 질문("참여도가 떨어진 페이지")은 시드에서 성립하지 않았다. 모델이 캠페인을 짚지 못한 것은 이 때문이다.
- 수정:
  - 질문을 "어제는 그 전 7일보다 페이지뷰가 크게 줄어든 페이지가 있어? 있다면 원인을 분석해 줘"로 바꿨다.
  - `check_sql`에 "/products* 어제 페이지뷰 < 그 전 7일 일평균의 75%" 조건을 더했다(어제 1,670 / 일평균 2,834).

#### diag-09: 전환 사실 추가

- 질문은 "유입과 전환 관점"인데 사실 항목은 유입(소스 3개, 신규 방문자)뿐이었다.
- 캠페인 전환율은 최근 14일 6.3%로 캠페인 외 유입(7.6%)보다 낮다. 캠페인 안에서는 naver cpc 8.0%, kakao push 5.6%, instagram cpc 3.7% 순이다(캠페인 기간 기준, 시드 intent와 같은 순서).
- 수정:
  - `campaign_conversion` 사실을 추가했다. 키워드는 [전환] + [낮, 못미, 밑돌, 하회, 떨어]다. `check_sql`은 캠페인 전환율 < 캠페인 외 전환율이다.
  - `required`를 1 → 2로 올렸다. 소스 사실은 거의 모든 답변에 나오므로, 신규 유입이나 전환 중 하나를 더 짚어야 통과한다.
- 기존 리포트의 diag-09 summary 10건에 새 사실을 적용하면 7건이 잡혔다. 잡히지 않은 로컬 답변은 캠페인 전환율만 말하고 비교하지 않은 답변이라 의도와 맞다. 리포트에는 findings 본문이 없어서 전체를 다시 채점하지는 못했다.

### 3. diagnose 예산 평가 (gpt-6-luna, 입력 토큰 상한 해제, judge 없음, 1회)

리포트: `20261126-1105-analysis-gpt-6-luna-budget-cap0`

| 항목 | 값 |
| --- | --- |
| 통과율 | 66.7% (8/12) |
| 강제 결론 / 예산 소진 | 0건 / 0건 |
| diagnose 10건 SQL 시도 | 7회 5건, 5회 2건, 3회 1건, 8회 이상 2건(diag-08 8회, diag-12 9회 중 1회 실패) |
| 질문당 입력 / 출력(추론) 토큰 | 28,054 / 6,779 (4,320) |
| 지연 평균 | 64.0s |

- 상한 4,800 아래에서 실행마다 4~5건이던 강제 결론이 0건이 됐다. SQL 상한에 닿은 실행도 결론을 정상으로 냈다.
- 대부분 SQL 7회에서 멈췄다. 예산 80% 안내(8회의 80% = 6.4회) 뒤에 결론을 낸 것으로 보인다.
- **결정: diagnose SQL 상한(8)과 안내 문구를 바꾸지 않는다.** 11-26의 강제 결론 증가는 입력 토큰 상한 때문이었다.
- 문항별:
  - diag-01: 새 질문으로 처음 통과했다. /products 44% 감소와 nov_mega_sale 세션 급감을 짚었다. 다만 "캠페인이 직접 일으켰다고 단정할 수 없다"고 유보했다.
  - diag-09: 실패. 전환 사실은 찾았지만("전환율은 전체보다 낮다", 인스타그램 효율 약함), 답변에 kakao가 없어 소스 사실(3개 모두 필요)을 놓쳤다. 이전 기준(required 1)이었어도 실패했을 답변이다.
  - diag-02(실패 단계), diag-10, diag-11은 이전 실행에서도 번갈아 틀린 문항이다.
- 평가 토큰: 입력 약 33.7만, 출력 약 8.1만(사전 추정 35만 / 8만).

### 4. diag-09 소스 사실 완화 (`evals/judges.py`, `evals/datasets/analysis_questions.yaml`)

- 3절의 diag-09 답변은 naver와 instagram만 짚고 kakao를 빼서 소스 사실을 놓쳤다. 전환 관점까지 다루면 주력(naver)과 저효율(instagram) 소스만 짚는 경우가 많다.
- 사실 항목에 `min_groups`를 추가했다. 이 값은 찾아야 하는 키워드 그룹 수이며, 값이 없으면 지금처럼 모든 그룹이 필요하다. 평가셋 머리 주석에도 설명을 넣었다.
- diag-09 `campaign_sources`에 `min_groups: 2`를 지정했다(소스 3개 중 2개 이상).
- 테스트: `test_fact_found_min_groups`를 추가했다.
- 3절 리포트의 diag-09 summary에 새 기준을 적용하면 `campaign_sources`·`campaign_conversion`을 모두 찾아 통과한다. 평가는 다시 돌리지 않았다.

### 5. CI의 LLM 회귀 평가를 수동 실행으로 제한 (`.github/workflows/agent.yml`)

- 저장소에 `OPENAI_API_KEY` 시크릿을 등록하면, `agent/` 등을 건드린 PR에 push할 때마다 LLM 단계(golden 축소셋 10문항 + 에이전트 안전성 5문항, 실행당 약 4~5만 토큰 추정)가 돌게 된다.
- LLM 단계의 조건에 `github.event_name == 'workflow_dispatch'`를 추가했다. PR에서는 lint·단위 테스트·DB 통합 테스트·`check`·검색 평가만 돌고, LLM 평가는 Actions에서 수동으로 실행할 때만 돈다(`full` 입력으로 전체 평가셋 선택 가능).
- 추가 수정: 워크플로 전체를 수동 실행으로 바꿨다. `pull_request` 트리거를 지웠고, LLM 단계의 `workflow_dispatch` 조건은 불필요해져 되돌렸다. 이제 `test`·`eval` job도 PR에서 자동으로 돌지 않는다.
